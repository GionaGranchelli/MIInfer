# EXP-0320 — M25 P512 continuation crash and resident FFN repair

**Status:** RETEST; source repair built, GPU validation pending  
**Milestone:** M25  
**Date:** 2026-09-12  
**Baseline commit:** `e0bae93`  
**Candidate:** working tree after `e0bae93`

## Question

Does the qualified H/I P512 path execute a real continuation after prefill?

## Failure

The earlier `--repeat-p512-check` was a false positive: with
`max_new_tokens=1`, `generate_layer_major()` computes only the first token
from the final prefill hidden state. It does not call `step()` or execute a
decode layer.

An exact H/I run with `--max-tokens 128 --no-stream` reached the 512-token
prefill, then crashed during the first continuation step. The first
experiment used default HIP graph capture; the matched `MIINFER_HIP_GRAPH=0`
run also crashed, so graph capture was not the cause.

`coredumpctl` recorded SIGSEGV in `FullAttentionLayer::run()` from
`ensure_graph_captured()`. The faulting instruction was identified with
`objdump` at `0x15df36`:

```text
mov 0x4e8(%r14), %rax
mov (%rax), %rdi
call launch_m23_q4k_repacked_mmq
```

Offset `0x4e8` is `resident_ffn_gate_mmq`.

## Root cause

`resident_m23_all` selected the M23 decode path and set
`resident_m23_ffn=true`. When `prefill_mx_ffn=true`, the constructor packed
only Mx FFN weights, then changed `resident_m23_ffn` back to false and skipped
the M23 FFN upload. Decode still followed the `resident_m23_all` branch and
dereferenced the null M23 FFN buffer.

## Repair

- Require the M23 resident type contract before enabling `resident_m23_all`.
- Pack both Mx FFN weights for wide prefill and M23 FFN weights for resident
  decode when H/I is enabled.
- Fail if resident M23 FFN packing is unexpectedly empty.
- Change `--repeat-p512-check` to request two generated tokens, which forces
  one actual continuation layer, and report the second token and its latency.

## Verification

The Release `miinfer` target rebuilt successfully after the repair. Runtime
verification could not be completed in this session: the crash left ROCm in a
contaminated state, and `rocm-smi --gpureset` requires a privileged password.
The 13.8 GiB compressed core generated by the first run was retained by the
system coredump service; no core was generated by the bounded follow-up.

## Decision

**RETEST.** The source defect is localized and repaired, but H/I must not be
promoted until a privileged cold-state run passes:

```text
P512 prefill → first token → one real continuation token → repeat P512
```
